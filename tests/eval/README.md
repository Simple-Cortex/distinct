# Calibration and evaluation suite

Goal: measure whether a change to the engine or the critique guides makes the agent catch more planted logo flaws and raise fewer false flags.

Everything committed here is synthetic: marks generated by code in `tests/fixtures/calibration/generate.mjs`, under the repo licence. No client marks, no third-party trademarks. The fixture directory is not in `runtime-manifest.json`, so it does not ship with the skill.

## Layer 1: engine calibration (CI, deterministic)

```
cargo build -p distinct-cli
node --test tests/eval/
```

Skips with a clear message when `distinct-rs` is not built (set `DISTINCT_RS_BIN` to point at a binary). It checks:

1. Fixtures regenerate byte-identically (no drift). To regenerate: `node tests/fixtures/calibration/generate.mjs`, then confirm `git diff` is clean.
2. For each fixture, in a fresh workspace: `logo inspect`, `logo proof` when inspected, `color check` for colour fixtures. It asserts `expect_engine` and the APCA Lc ranges. The ranges come from the APCA-W3 0.1.9 reference implementation, not from the engine.
3. A coverage table on stdout: for each planted flaw type, whether the engine measures it today or only a critic can judge it. `measured: X/N flaw types` is the number that 0.5 and 0.6 should raise.

F5 is `judged`, not `measured`: the engine's `min_feature_px` is an axis-run count and does not detect dot or hatch collapse.

F9 uses `clipPath` on purpose, so the engine reports `unsupported_content` and `logo proof` is blocked. The packet builder skips fixtures it cannot render.

## Layer 2: critic eval (host-run, costs tokens, never in CI)

The rubric item ids (`appropriate`, `simple`, `distinctiveness`, `small_size_legibility`, ... `memorable`) come from `references/critique.md`, shipped in the docs PR Simple-Cortex/distinct#5. Until that is merged, the file does not exist here and the example runner exits with a clear message. The manifest test hardcodes the id list and checks every `rubric_item` against it. The manifest's top-level `measured_items` (`colour_contrast`, `engine_safe`) is the single list of items the engine measures; the scorer allows MEASURED findings only on those.

Warning: running a critic calls a paid model, once per run (twice with the order check). Nothing in this repo runs one for you.

```
node tests/eval/critic/build-packet.mjs --seed 1 --out /tmp/run1 [--lineup] [--reverse]
```

- Renders each control and flawed fixture through `logo proof` at 16, 24, 64 and 512 px on a light and a dark plate, plus a mirrored and an inverted variant (transformed SVG copies; colour fixtures swap their two plates instead, no new engine features).
- Opaque labels `K-01`... in seeded random order. `--lineup` adds the reference marks as unlabelled "existing marks" (`E-01`...). `--reverse` keeps the same labels and lists them in reverse order.
- Writes `<out>/packet/` (PNGs and a neutral `index.md`) and `<out>/key.json` (label to fixture id). Never show `key.json`, `skipped.json` or the manifest to the critic.

The critic writes `critic.json`:

```
{"candidates":[{"label":"K-01","verdict":"present|rework|drop",
  "findings":[{"item":"<rubric item>","class":"MEASURED|JUDGED|OBSERVED","severity":"minor|major|blocker","text":"..."}]}]}
```

Score it (pure, no network):

```
node tests/eval/critic/score.mjs --key /tmp/run1/key.json --critic critic.json \
  [--reverse-critic critic-rev.json] [--manifest path]
```

Report: `flaw_recall` (overall and per flaw type), `control_false_flag_rate`, `self_flagged_but_presented` (should be 0), `verdict_accuracy`, `order_consistency` (needs a reverse run), `measured_claim_violations` (a MEASURED finding on an item not in `measured_items`). Reference labels are ignored. A control missing from the critic output counts as a false flag and an accuracy miss. An unknown label is an error.

`critic/run-claude-code.example.sh` is an example host runner. It starts a fresh headless critic that sees only `packet/` and `references/critique.md`.

### Comparing two branches

1. Check out branch A, run the engine build, then build and run the critic with a fixed seed: `--seed 1`, forward run, then the same seed with `--reverse`.
2. Score both runs together with `--reverse-critic`.
3. Repeat on branch B with the same seed and the same critic model.
4. Compare the two reports. Use several seeds for anything you intend to act on; one run is noisy.

Results go to `tests/eval/results/` (gitignored).

## Layer 3: private set (local only)

Set `DISTINCT_EVAL_PRIVATE=<dir>` to a folder holding a `manifest.json` in the same format and the real SVGs. Layers 1 and 2 add these fixtures (ids prefixed `private:`) and never copy them into the repo. Their contents are never printed. `tests/eval/private/` is gitignored and is a good place for the folder.

To build one from a past project, with ids and file paths only:

1. Pick past candidates the owner accepted (role `control`) and rejected (role `flawed`). Name each by an opaque id such as `P1`, `P2`.
2. Copy each SVG into `<dir>/svg/<id>.svg`. Keep only engine-safe elements (see `references/commands-assets.md`).
3. Write `<dir>/manifest.json`: `{"version":1,"fixtures":[{"id":"P1","file":"svg/P1.svg","role":"flawed","flaws":[{"type":"<owner's reason>","rubric_item":"<rubric item>","detectable":"judged","note":"..."}],"colours":null}]}`. `expect_engine` is optional for private fixtures. The owner's real verdict is the ground truth.
